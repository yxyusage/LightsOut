# 设计决策记录

本文档记录 PRD 中没有明确指定、或存在自相矛盾、需要工程判断的地方，以及我们的处理方式与理由。

---

## 1. 作品形态：Web 版与原生 Android 版的取舍

### 冲突

- **赛事要求**（《赛事介绍》六、作品要求 1.2 / 1.3 / 1.5）：作品需具备「可独立运行、可交互体验、
  **可被调用**」的技术特性，符合支付宝内容接入规范；必须是「可实际运行 / 访问的智能体，
  而非单纯的概念描述、效果图或演示文稿」；投稿及评审期间需「保持可访问、可体验状态」。
  提交方式二选一：**公网可访问的 URL**，或 ZIP 包。
- **PRD 要求**：原生 Android 应用，依赖设备管理员、前台服务保活、悬浮窗接管、防卸载等系统级能力。

原生 APK 无法满足「公网 URL 可访问」与「可被调用」，且提交页的 ZIP 通道标注为「即将上线」。

### 决策

**以 Web / PWA 为交付形态参赛**，同时把原生端作为独立的平台实现保留在仓库中。

Web 版通过「添加到主屏幕」以 standalone 模式全屏独立运行，配合 Wake Lock 与全屏接管，
在仪式感与强制感上尽可能逼近原生体验；PRD 中真正需要系统权限的部分
（禁止强制停止、防卸载、拦截 HOME 键）明确标注为「需原生端」。

### 理由

1. 赛事资格是第一优先级 —— 作品必须能被评审打开；
2. 诚实标注能力边界比夸大宣传更安全。赛事季度评审维度里有「**责任可信**：是否具备基本的
   安全、合规、隐私和可信保障」，把「专注接管」包装成「系统封锁」反而是减分项；
3. PRD 1.5 本身就写了「PC 端同步规划开发」，说明多形态并非背离文档。

## 2. PRD 2.2.3「当日」的语义澄清

### 冲突

PRD 2.2.3 原文：总时长耗尽后「自动从应用退回熄灯黑屏界面，**当日**无法再使用任何白名单应用」。

字面理解是按**日历日**计费，0 点重置。但熄灯时段默认是 23:00 → 次日 07:00，**横跨午夜**。
如果真在 0 点重置，用户只要在 23:50 用掉 30 分钟、0:10 再拿 30 分钟，
就能在**同一次熄灯**里用掉双倍额度。这显然不是产品意图。

### 决策

把「计费周期」抽象为**由调用方注入的 periodKey**：

- 核心包的**默认实现按日历日**（严格贴合 PRD 字面语义），有测试覆盖；
- **应用层实际传入「当前熄灯时段的开始日」**，这样一次熄灯（哪怕跨过午夜）
  共用一个额度池，下一次熄灯开始时自然重置，也有测试覆盖。

两种行为都由 `tests/whitelist.test.js` 验证，切换只需换一个 `getPeriodKey`。

## 3. PRD 2.2.3「共用总时长」与「电话短信无时长限制」的冲突

### 冲突

同一节里两句话互相矛盾：

- 「所有白名单应用**共用**总可用时长，支持用户自定义时长，上限为 60 分钟」
- 「系统自带电话、短信默认加入白名单且不可移除、**无时长限制**」

### 决策

给白名单应用增加 `countsAgainstQuota` 字段：

- 电话、短信：`countsAgainstQuota: false`，**不占用**总时长池；
- 其他所有应用：`countsAgainstQuota: true`，共用同一个池子。

并且 `migrateSettings()` 会**强制**把系统应用修正回 `countsAgainstQuota: false` 与
`removable: false` —— 即使用户手工改了 localStorage 也无法绕过（有测试覆盖）。

### 理由

这样理解可以让两句话同时成立，也符合常识：紧急联络能力不应该被娱乐预算限制。

## 4. 调休上班日按工作日处理

### 背景

PRD 只定义了「工作日」与「周末」两套时段。但中国的法定调休会把某个周六变成上班日
（例如 2026-02-28 是春节调休的上班周六）。

### 决策

**调休上班日的晚上按工作日时段熄灯。** 核心包内置了 2026 年全部 6 个调休上班日
（来自国务院办公厅通知），并提供 `respectMakeupWorkdays` 开关以便需要时退回 PRD 字面语义。

### 理由

用户当天确实在上班，作息节奏与工作日一致，按工作日时段熄灯才是符合产品意图的行为。

## 5. 危害科普数据的真实性纪律

### 背景

赛事《禁止内容》4.7 明确禁止「**虚构数据、伪造案例或误导用户**的内容」。
而睡眠类产品最容易出现的就是随口编造的吓人数字。

### 决策

三条纪律，并在代码层面强制：

1. **只收录能在原始论文或官方通报中查到的结论**；
2. **每条危害数据必须绑定 `source` 键**，界面可一键展开溯源（有测试断言「至少 5 条带来源」）；
3. **不写伪精确数字**，措辞保留研究结论原本的强度 —— 例如写「风险升高」而不是「必然致癌」。

当前收录的来源：

| 来源键 | 文献 |
| --- | --- |
| `prather2015` | Prather AA et al., *Sleep*, 2015 —— 睡眠 ≤6 小时者感冒风险是 >7 小时者的 4 倍以上 |
| `williamson2000` | Williamson AM & Feyer AM, *Occup Environ Med*, 2000 —— 清醒 17 小时 ≈ BAC 0.05%，24 小时 ≈ 0.10% |
| `iarc2019` | IARC 专著第 124 卷，2019 —— 昼夜节律紊乱的轮班工作列为 2A 类 |
| `xie2013` | Xie L et al., *Science*, 2013 —— 睡眠期间类淋巴系统清除代谢废物 |
| `yoo2007` | Yoo SS et al., *Current Biology*, 2007 —— 缺觉削弱前额叶对杏仁核的调控 |

节假日数据同样有出处：《国务院办公厅关于2026年部分节假日安排的通知》（国办发明电〔2025〕7号），
并且测试会**反向验证**每个日期是否落在通知中写明的星期上 —— 这是防止抄错一天最有效的手段。

## 6. AI 文案只作为「开场第一句」

### 背景

PRD 2.4：「开启 AI 文案功能后，**替换为**场景化生成的个性化文案」。

### 决策

AI 生成的场景化文案作为**进入熄灯界面后的第一句**展示一轮（默认 12 秒），
之后交还给内置文案库继续轮播。

### 理由

1. 保留「它知道今天是什么日子」的惊喜感 —— 这恰恰是 AI 在传统产品里难以实现的价值；
2. AI 只在**进入熄灯的瞬间**请求一次（结果按日期 + 场景缓存），
   不会因为接口波动、限流或超时导致黑屏界面断流无文案；
3. 任何失败都静默降级到本地文案库，**绝不阻断熄灯流程**。

## 7. 紧急解除密码不是安全机制

### 背景

PRD 2.2.5 要求「输入预设密码后可退出熄灯模式」。

### 决策

使用**固定域分隔前缀 + SHA-256** 做摘要（`xideng::emergency::v1|` + 密码），
**不使用**慢哈希 / KDF，也不存储盐值。

### 理由

这是**防冲动的一次减速带**，挡住的是「半夜手滑想退出」的瞬时决定，不是攻击者。
密码摘要与全部设置一样只存在用户本机，能读到 localStorage 的人本来就能直接改设置。
引入盐值与迭代参数只会增加复杂度，却挡不住这类访问。

这个取舍是有意为之，已写入代码注释。同时：

- 未设置密码时**永远不通过**（避免空密码解锁，有测试覆盖）；
- 密码校验在**额度扣减之前**，密码错误不会消耗用户宝贵的解除次数（有测试覆盖）；
- 密码强度检查会提示「纯数字容易误触通过」。

## 8. 演示模式

### 背景

赛事评审不可能等到晚上 23:00 才看效果。

### 决策

主页提供「立即体验熄灯模式」，进入 2 分钟的演示熄灯界面。

### 它不能被用来绕过熄灯

- 演示模式只出现在**熄灯界面与主页**，不会让真实熄灯失效；
- `effectivePhase()` 中演示模式是**优先返回 active** 的短路分支 —— 它只能把状态推向 active，
  永远无法把 active 推离；
- 演示模式**不安装**防绕过守卫（历史栈围栏、beforeunload），并在顶部常驻「退出演示」按钮 ——
  这是为了不把评审困在界面里，是一个刻意的可用性让步；
- 2 分钟后自动过期，会话级存储。

## 9. Web 端白名单的实现边界

浏览器无法启动其它原生 App，因此 Web 端的白名单实现为：

- **系统电话 / 短信**：使用 `tel:` / `sms:` 协议，在移动端可以真实拨出与发送短信；
- **自定义应用**：用户填写名称 + 打开地址，在新标签页打开；
- **计时**：从「离开本页」开始计时，回到页面时按实际经过时间一次性结算，
  超出剩余额度则立刻退回并提示。

这个实现是诚实的：它能真实地限制「在熄灯时段内使用被允许的应用」的总时间，
但无法阻止用户在浏览器之外使用其它 App —— 那需要原生端。

## 10. 技术选型：为什么零依赖、零构建

| 备选 | 为什么没选 |
| --- | --- |
| React + Vite | 需要 npm 安装与构建步骤；依赖树的供应链与长期维护成本；对一个单页应用而言收益不足 |
| 支付宝小程序 DSL | 最贴合支付宝生态，但需要支付宝开发者工具与账号才能预览，无法在本地验证运行 |
| 引入 UI 组件库 | 本项目是深色极简风，组件库的默认样式反而要大量覆盖 |

选择**原生 ES Module + 零依赖**带来的实际好处：

- 离线可用（PRD 2.3 要求熄屏可持续播放，赛事要求评审期间可体验）；
- 没有 `node_modules`，十年后仍能直接打开；
- 模块边界清晰，浏览器直接就是调试器。

代价是需要自己写约 200 行的 DOM 工具与构建脚本 —— 完全值得。

## 11. 许可与仓库命名

- **许可**：MIT。赛事不限制开源，MIT 最利于复用与传播。
- **语言**：代码注释、文档、界面均为中文（目标用户与赛事都在中文语境）；
  个别标识符保留英文以便与标准 API 对齐。
- **仓库名**：建议 `xideng`（拼音，简短且不易重名），README 中保留中文全称
  「熄灯早睡 / Lights Out」以便检索。
